# Cray / 主板联调更新（2026-10-11）

作者：COEX、Xuanting Liu

## 当前有效结论：恢复原遥测字段，根因尚未确认

用户后来发现目标板断电时 Cray 仍显示红外 Detected。已证实普通反馈面板只绑定缓存布尔值，不检查新回包时间，断开/重连也未清除该值。最新日志（本地 17:12:33）只有 1 个发射机握手回复，没有主板反馈，不能据界面 Detected 认定目标主板在线。

已修复 Cray：记录普通反馈接收时间及原始车号；无回包显示“无回包”，5 秒无新普通反馈显示“回包超时”，隐藏过期电压/轮速；断开/重连清除会话反馈时间与红外状态；保留实时/日志来源标识并附加最近回包车号。此时间判断仅指反馈新鲜度，不保证普通事件式反馈每 5 秒必须上报，也不认证发送设备的物理身份。

另修复 Game Detect 将零电压直接视为离线的问题：现在按最近回包时间置灰，未接 POWER 不再仅因电压零被当作离线。真实 QML 测试覆盖红外缓存过期、断开清除、初始无回包及零电压新回包。姿态 AA5510 缺失根因仍未确认，界面修复不代表无线已修复。正常主板固件本轮未改变，不需重刷。

以下各节记录排查过程，不代表所有早期假设已成立。用户随后报告 `g_telemetry_radio.completed=72`、`failed=0`、`unconfirmed=2`、`last_status=0x2E`。这确认有多次本地 TX_DS，但不确认远端接收。

重新对比迁移前 `a96fdef` / `6e3b169`：两种包头原本就是 FF02 和 AA5510，无线长度、地址配置及原始发送实现未在迁移时改变。不能认定新包头导致不兼容，也不能根据磁盘上的未知发射机版本认定实际设备会过滤。

排查期间加入的 byte 4 校准诊断扩展缺乏中间接收器兼容验证，现已撤回，恢复仅 0/1 的红外状态；本地 Watch 诊断保留。由于该扩展晚于最初故障报告，它不能解释最初的全部症状。当前 Cray 对无扩展帧显示通用校准提示；早期实验帧仍可解码。

`tests/mpu6050/test_telemetry_history.py` 直接编译历史打包函数，与当前函数对同一输入逐字节比较，含 606 种校准诊断组合。全部 25 字节一致；这是软件格式验证，不是无线回归测试。Keil 和 Cray 编译、协议与界面测试通过。

本轮对照产物为 `output/monitor/SRC_Firmware_wire_restore.hex`。先保持现有 Cray、发射机、接线和测试模式，只替换该主板固件并复查 serial_rx.log。尚未把任务负载、无 POWER 时的 I2C3 重试或 ADC 改缓存导致的时序变化认定为根因，也未为此修改调度或基础配置。

## 已修改

- Cray 的 Game Detect 连接现在执行与手动模式相同的发射机频率握手；仍禁止在该模式发送运动控制命令。适用于用户确认的同一发射机。
- 主板周期状态广播不再受最近一个控制包类型限制。注意：`PACKET_Normal` 实际为 0，因此原程序冷启动本来就满足这个条件；本次修复的是收到其他类型包后可能停止广播的问题。
- 增加校准进度、最近一次校准重置原因的回传和显示。保留先前根据本板正反面测量计算的 Z 轴修正，未调整静止判定门限。
- 未修改 CubeMX 基础配置、引脚或外设初始化。

## 实测步骤

1. 烧录 `output/monitor/SRC_Firmware_monitor.hex`。
2. 关闭旧 Cray，运行 `output/monitor/cray/Cray.exe`，保留其目录内的 Qt 依赖。源代码也已同步修改于 `E:/SRC/Develop_Cray/Cray`，可用 Qt Creator 重新构建。
3. 选择相同串口、频率，勾选 Game Detect 后连接。查看实际车号的状态；界面车号为 0 起始，固件 `g_robot.num` 减 1。
4. 静置主板至少 10 秒。如果仍未校准完成，记录状态栏完整文字及进度是否反复归零。

| Watch 字段 `g_robot.attitude.calibration_reason` | 含义 |
| --- | --- |
| 0 | 尚无拒绝记录，或已完成校准 |
| 1 | 加速度模长不在 0.90～1.10 g |
| 2 | 任一轴角速度绝对值超过 5 °/s |
| 3 | 校准窗口内任一轴角速度方差超过 0.25 (°/s)² |
| 4 | 相邻有效样本间隔超过 100 ms |
| 5 | 读取失败或任务检测到长时间无新样本；恢复后重新采集 |

`g_robot.attitude.calibration_progress` 为 0～100%。Cray 将其压缩为 16 档传输，因此界面进度约以 6～7% 跳变。原因表示最近一次重置，后续采集过程中保留，直到校准完成清零；不是每帧都发生该故障。

若界面仍无状态，读取以上两个字段、`accel_g[0..2]`、`gyro_dps[0..2]`，并观察 `sequence` 是否变化。新增诊断尚不能替代板上数据，持续校准的实际原因仍待确认。

## 协议与验证

24 字节 `AA 55 10` 帧长度、CRC、姿态字段保持原样。字节 4 的 bit 0 仍为红外状态；bit 1～3 增加校准原因，bit 4～7 增加进度。当前 Cray 原有红外解码只读取 bit 0。

- Keil 编译、链接、生成 HEX；工具链仍有原有授权警告。
- MPU6050 驱动故障注入、正反面 Z 轴修正与校准测试通过。
- 滤波测试覆盖各项校准重置原因及恢复，固件真实打包函数测试通过。
- Cray 实际解析器与主 QML 界面测试通过：同一固件样本帧、CRC、分片、模式、校准原因/进度、超时/断开状态。
- `output/monitor/cray_calibration.png` 为模拟数据的界面验证截图，不是硬件测量。

无线链路和持续校准原因仍需在实物上验证；软件测试不等同于整机联调通过。

## 后续实测：红外正常、姿态等待、Game Detect 无状态

本地 `E:/SRC/发射机代码/F4_NRF_24L01_R/F4_NRF_24L01_R/Core/Src/main.c:117` 的转发条件仅接受 `FF 02`，会丢弃 `AA 55 10`。若此工程对应实际发射机固件，可直接解释两种新遥测同时缺失；实际烧录工程尚待用户确认，暂未修改发射机代码。之前只验证两端解析，未覆盖该中间转发条件，不能把普通红外回包成功当作新遥测全链路已通过。

此外，OLED 的 Logo 在初始化后被下一次状态显示立即清除。已在显示任务初始化后增加 `osDelay(2000U)`；期间不持有 I2C2 互斥锁。固件重新编译为 0 错误、1 条原有工具链授权警告，上述 monitor HEX/AXF 已更新。此修改解决 Logo 停留时间，不代表已诊断持续黑屏。

用户随后确认 OLED 后续状态显示正常，并说明同一发射机以前能显示姿态和 Game Detect。因此磁盘上的旧发射机工程不能视为实际固件，过滤条件目前只是候选原因，不能据此要求升级发射机。

实际原始串口日志位于 `E:/SRC/Develop_Cray/Cray/build/CrayR/serial_rx.log`：共 600 字节，1 个握手回复、23 个车号 1 的 FF02 帧，没有 AA55（已拼接检查读取边界）；用户确认未重连且切换了 Game Detect，切换后无任何接收记录。

主板两个提交计数均增长后，新增 `g_telemetry_radio`：`completed` 统计恢复 RX 前读到的 TX_DS；`failed` 统计 MAX_RT 或无效 0xFF 状态；`unconfirmed` 统计未观察到上述结果；`last_status` 保留原始 STATUS。仅统计 AA5510，读取在原有清 FIFO/清 IRQ 之前完成。TX_DS 只确认本地无线发送完成，当前无 ACK，不能证明远端接收；缺少 TX_DS 也可能涉及状态被提前清除。真实发送/恢复 RX 函数的模拟状态测试及 Keil 编译通过。monitor HEX/AXF 已更新，未修改发射机、Cray 或基础配置。

新增 Watch 字段 `g_game_telemetry_calls`（周期遥测服务调用次数）及 `g_game_telemetry_tx_count`（遥测提交给无线驱动次数，不是接收确认）。进入 Game Detect 并停止普通控制指令后，观察运行 10 秒期间两个值是否增长；正常调度下后者约每 260 ms 增加一次。结合 `g_robot.mode`、`g_robot.num` 和 `g_robot.attitude.flags` 可以区分任务/发送调度与后续接收链路问题。此诊断不改变发送时序。
